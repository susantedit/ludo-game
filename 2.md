## 1. The main product

Ludora starts with two games:

* 🎲 **Ludo**
* 🐍 **Snake & Ladder**

But the long-term identity is:

> **Classic board games with modern game modes, progression and social play.**

The important distinction is that **offline play must be complete**.

A user should be able to install Ludora, turn off Wi-Fi/mobile data, and still play.

### Offline modes

**Ludo**

* Player vs AI
* Local 2-player
* Local 3-player
* Local 4-player
* Human + AI combinations
* Multiple AI difficulties
* Custom rules
* Different boards/themes

**Snake & Ladder**

* Player vs AI
* Local multiplayer
* 2–4 players
* Different board themes
* Optional power-ups
* Different rule sets

No login should be required for offline play.

# 3. The big differentiator: Remix Mode

This should become one of Ludora's signature features.

Instead of only:

> Ludo

give users:

> ⚡ **Ludora Remix**

The game modifies the traditional rules.

Examples:

### Ludo Chaos

Random events can happen:

* Double roll
* Reverse movement
* Temporary safe zone
* Random teleport
* Extra turn
* Token swap

### Snake & Ladder Chaos

Special squares can:

* Teleport you
* Give you a shield
* Reverse another player
* Give another roll
* Create temporary ladders

### Ludo + Snake

This is where Ludora becomes more distinctive.

The Ludo board can contain special snake/ladder spaces.

So the player knows the traditional game but gets unexpected events.

Later you can add:

> **Create Your Rules**

Players choose:

```text
Players: 4
Turn timer: 15 sec

☑ Double six
☑ Power cards
☑ Chaos events
☐ Token swap

Difficulty: Normal
```

Then create a room.

That gives Ludora a system you can expand for years.

# 4. Offline progression

This is important because you specifically want offline support.

Don't make progression dependent entirely on your backend.

Store the local profile securely on the device.

For example:

```text
LEVEL 18

Susant
⭐ 1,840 XP

Games       127
Wins         71
Win Rate    55.9%

🎲 Dice collected: 8/25
🧩 Boards: 5/12
🏆 Achievements: 14/40
```

When the user later goes online, appropriate online data can sync.

You need to design the sync system carefully so local progress cannot simply be trusted for competitive online rewards.

# 6. Ads only when online

This needs a very clear architecture.

### Offline

```text
Internet: ❌

No ads
No ad requests
No online matchmaking
No network dependency

Game continues normally
```

### Online

```text
Internet: ✅

Online features available
Ads may be loaded
```

I would **not** put ads in the middle of a player's turn.

That would hurt the actual game experience.

Instead consider:

### Home-screen banner

Online only.

### Rewarded ad

Optional:

> 🎁 Watch an ad to receive 50 coins

### Interstitial

Only at a natural break such as after a completed match, with frequency limits.

And never make:

> "Watch an ad or you can't continue."

The game should remain usable without watching ads.

Also, build an **AdProvider abstraction** rather than hard-coding an ad SDK everywhere:

```text
AdService
 ├── isOnline()
 ├── canShowBanner()
 ├── showRewarded()
 └── showInterstitial()
```

That makes it easier to change providers later.

without needing to render the game.

# 8. Online architecture

For online multiplayer, the server must be authoritative.

Do **not** trust the client to tell the server:

> "I rolled a 6 and moved my token here."

Instead:

```text
Client
  ↓
"ROLL_DICE"
  ↓
Server validates turn
  ↓
Server generates roll
  ↓
Server calculates legal move
  ↓
Server updates state
  ↓
Clients receive state
```

This is especially important once ranked matches or valuable rewards exist.

Potential architecture:

```text
Android Client
      │
      ▼
Realtime Gateway
      │
      ▼
Game Room Server
      │
      ├── Ludo Engine
      ├── Snake Engine
      └── Remix Engine
      │
      ▼
Database
```

For MVP, we can keep the backend small and expand only when online multiplayer actually works.

# 9. Security

Your requested:

`[create-security-implementation-plan]`

fits this project well.

We should treat the online mode as untrusted-client multiplayer.

Security needs to cover:

* Authentication
* Room authorization
* Server-side game validation
* Rate limiting
* Invalid moves
* Replay protection
* Match IDs
* Player permissions
* Anti-cheat
* Secure random dice generation
* Reward validation
* Ad reward verification
* API abuse
* WebSocket abuse
* Reconnection
* Account/session security

The offline game doesn't need to contact the backend simply to roll a dice.
